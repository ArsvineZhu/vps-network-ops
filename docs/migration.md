# 将现有部署迁移到新主机

迁移目标是能从同一份源码和私有输入重建系统，并分批切换客户端。当前 Ansible 只安装新主机，不会把现网零散配置自动归并，也没有自动原地升级或回滚功能。

## 1. 先记录真实现状，再选择迁移范围

- 分别保存**正在运行的配置、磁盘上的启动配置、客户端当前选择的配置或订阅**。三者可能不同，不能拿任何一份代替另外两份。
- 核对现用 Mihomo、Caddy、内核、TCP 指纹源码和单元版本，以及监听端口、设备身份、UDP 策略、namespace、veth、路由、防火墙、tc、MTU、BBR、TLS 与续期方式。
- 额外记录管理通道：SSH 端口和密钥、云控制台、Tailscale、UFW、云防火墙、客户端精确管理直连例外。订阅里的管理例外不意味着服务端应该放行代理访问 VPS 自身。
- 标注每一项来源、检查时间和验证状态。历史部署记录只能作为排查线索；正在进行的 UDP、BBR 或防火墙现场调整必须以最新状态重新核对。
- 全量快照和命令输出可能含 UUID、密码、私钥、订阅路径、成员信息和真实地址。只存仓库外受限目录，分享前制作脱敏副本。

优先使用既有[只读诊断工具](../skills/operate-vps-network/scripts/USAGE.md)收集信息。读取、保存快照与修改远端配置是不同步骤；不要让盘点顺手变成服务重启。

## 2. 把实例差异映射到统一输入

1. **主机与协议：** 逐项填入目标主机、域名、监听和启用的协议。仅实现了 Hysteria2、AnyTLS 的生成器，不代表现网已经启用或完成客户端测试。
2. **设备身份：** 每设备使用稳定 ID，每协议保留独立认证材料。把旧身份到新 ID 的对应关系保存在私有迁移记录，不把真实凭据写进示例。
3. **出口策略：** 明确每设备选择 native、windows 或 ios。后两者复用设备级 TCP 出口，不为每种协议另建一套后端；后端失败必须失败关闭。
4. **UDP：** 明确选择 deny 或 direct。直接 UDP 使用受限前端原生出口，不声称经过 TCP 指纹后端，也不把未验证的 SOCKS UDP 当成成功。
5. **管理例外：** 保留确实需要的 IPv4、TCP 和 SSH 端口精确组合。不要为了“迁移后还能连”把整个网段或所有管理流量改成 DIRECT。
6. **TLS 与订阅：** 确认 DNS、域名覆盖、证书完整链、私钥权限和每设备订阅路径。新主机须能独立接收受控的证书更新，不能仅复制一次证书后就宣称续期完成。
7. **流量记录：** 保留旧数据及其来源说明。采样数据库不是精确计费数据，不能把新旧两机同一时段的观测直接相加而不说明重复或缺口。

构建后审阅 `plan.json`、清单与具体配置。看到模型无法表达的现网差异时先停止，选择扩展模型并测试或明确不迁移该功能；不要手改生成文件掩盖遗漏，否则下次构建会丢失修改。

## 3. 在独立新主机建立候选环境

- 按[部署手册](deployment.md)完成新主机预检和显式安装。对现有 `/etc/vps-network`、旧 Mihomo 或未知同名网络对象的拒绝，是需要人工检查的信号，不是应删除的障碍。
- 新主机先使用测试入口或测试域名，旧机保持运行。先拿一台受控客户端验证，不立即让所有设备更新订阅。
- 安装器不更改 UFW、Tailscale、SSH 或云防火墙。入站端口、转发规则与 DNS 的必要调整应单独审阅，并保留独立管理入口。
- 若必须迁移到同一台服务器，当前入口不适用。应先制定该实例的备份、停机、接管和回滚方案；不能把 `apply_changes=true` 当作自动导入现网的开关。

## 4. 分批验收与切换

1. **候选环境验收。** 完成部署手册的管理、身份、出口、TCP、UDP、订阅、用量和重启检查。正确凭据成功之外，也要检查错误凭据失败、私网拒绝和后端停止后的行为。
2. **单设备试运行。** 给一台设备新入口，确认客户端确实选择了新配置，并发起实际请求。下载订阅、通过配置解析、服务 active 都不能替代这一步。
3. **稳定运行。** 在预定观察窗口检查断线恢复、采样、日志、资源占用和证书检查。持续时间由实际用途决定，不能用一次测速通过直接结束验收。
4. **分批切换。** 按设备记录旧入口、新入口、测试结果和切换时间。需要通过 DNS 切换时预先规划 TTL，并考虑客户端和递归 DNS 的缓存；修改记录不会让所有流量瞬间迁移。
5. **保留旧入口。** 在验收窗口内保留旧机和能读取的旧配置。不要在客户端还可能引用旧订阅时删除证书、订阅或迁移资料。

分发新凭据或订阅属于对外分享，应按接收人和用途确认。仓库协作只共享代码和脱敏示例，不共享生产部署包；参与代码协作不自动意味着有权取得每个成员的凭据。

## 5. 回滚与部分失败

- 回滚的首要目标是让客户端重新使用已验证的旧入口，而不是立刻清理新机。先恢复客户端或已批准的 DNS 指向，再检查实际出口。
- 停止新机组件前确认是否仍有设备使用；按前端、后端、专用网络的依赖关系操作，且只有已经核对归属的对象才能清理。
- 不使用 `nft flush ruleset`、删除所有 namespace、重置 UFW 或关闭 Tailscale作为回滚步骤。它们可能影响管理通道及不属于本项目的服务。
- 安装失败会留下部分文件或服务，当前版本不自动恢复到安装前快照。保存失败阶段和私有日志；可丢弃测试机优先重建，生产节点则单独分析，不盲目重跑安装器。
- 原目录或备份被删除后，就不能继续把它列为可用回滚手段。只有已确认存在、可读并且与当前版本匹配的材料才算回滚准备。

## 6. 用量与凭据收尾

- 若需要迁移 SQLite，用正确的 SQLite 备份方式或停止采样后复制完整一致状态；不能只复制仍在写入中的 `.sqlite` 主文件而忽略 WAL。先离线验证，再由操作者决定是否导入。
- 迁移后的采样应保留明确的实例、协议、设备与时间范围。记录停机缺口和双机重叠，保留旧数据库为独立只读档案通常比直接合并更稳妥。
- 切换稳定且确认无需回滚后，再逐设备撤销旧凭据、下线旧订阅和停止旧服务。删除本地配置文件不等于服务端凭据已撤销。
- 如果旧机或私有包可能泄漏，按受影响范围轮换认证材料、订阅路径和证书私钥；不要仅移动同一份秘密而声称风险消除。

## 7. 迁移结束需要留下的记录

- 经审阅的 Git 提交、源码版本和固定二进制哈希，外加不含秘密的部署参数摘要。
- 每层验收结果、时间、测试客户端和未完成项目，特别是公网 UDP、真实指纹、未来证书续期及整机重启。
- 私有材料存放位置、权限、备份恢复方法以及负责人。公开仓库中只记录方法，不记录真实路径、凭据或订阅链接。
- 已撤销与仍保留的旧入口，以及下一次允许删除备份或停止旧机的条件。没有实际验证的步骤继续标记为待验收。

发布到 GitHub 前再次检查完整 Git 历史和待提交内容；仓库公开范围及发布动作需要单独确认。部署、分发凭据、推送代码是不同动作，互不默认授权。
