# DNS-01 证书与订阅发布作业

## 边界与选择

这份作业来自实际故障、签发与随后订阅部署记录。通用步骤不是自动执行脚本；最新完成范围见deployment-record.md。
HTTP-01 要求验证方访问公网 TCP80。服务器监听正常、UFW放行和本机curl成功，都不能证明公网可达。若验证连接超时，保留同时段外部探针与抓包证据，不能只据零抓包断言运营商封禁。
DNS-01 通过权威DNS TXT验证域名控制权，不依赖80/443入站；它不能修复HTTPS订阅端口的公网可达性。另用可达HTTPS端口发布时，客户端URL必须明确端口，仍需合法证书与独立外网测试。

## 1. 安装前先核对包与工具

- 先用 `unzip -l package.zip` 查看顶层目录，再决定解压目标。包自带目录时不要再假设脚本位于目标根目录。解压前检查绝对路径、`..`与符号链接，不把未知归档直接覆盖生产目录。
- 本次采用官方 acme.sh 3.1.6 的 dns_tencent，签名验证通过后安装，未安装cron、未修改profile。固定版本是复现基线，不代表永久最新。
- 本次确认的提交为 `807da6498377ee5e0cf43a78091f46f12dc59a89`。使用官方签名与独立核对的签名者身份验证，不能仅把下载的哈希与同一下载渠道比较就称可信。
- Caddy保留官方发行版，不为DNS插件未经审阅换成自编译二进制。

## 2. DNS权限与秘密输入

使用独立Tencent CAM程序访问身份，限目标DNSPod域。dns_tencent使用Tencent API3，不能用旧DNSPod API令牌替代而仍声称相同权限隔离。
按当前官方文档核对以下操作及资源支持：DescribeRecordList、DescribeRecordFilterList、CreateRecord、DeleteRecord；域资源模板为 `qcs::dnspod::uin/<ACCOUNT_UIN>:domain/<DOMAIN_ID>`。
这是整个DNS域的记录权限，不是仅 `_acme-challenge` TXT 权限。不要授予FullAccess或把resource改成星号来消除报错。凭据长期保存与续期属于持续访问，必须经过当次明确授权。

秘密不经聊天、命令行参数、shell历史、Git或调试日志传递。凭据文件父目录0700、文件0600；检查拥有者与符号链接。脚本用getpass隐藏输入并将GetPassWarning转为错误，避免静默退回回显输入。

Python 3.12实测踩坑：`open('/dev/tty', 'r+')` 会触发 non-seekable 错误。提示流应单独以 `'w'` 打开，再传给 `getpass.getpass(..., stream=tty)`；getpass自行取得控制终端输入。不要关闭隐藏输入保护来绕过问题。应在真正PTY中测试无回显、无TTY和termios失败；普通管道单元测试不能代替这些检查。

acme.sh的DNS插件还会保存凭据到其私有account.conf。轮换时同时检查专用凭据文件和acme.sh保存副本，不能只换一份。Caddy不应有权读取DNS API秘密。

## 3. 签发与证书验收

仅申请获批的订阅主机名，通过Let's Encrypt DNS-01。失败先看脱敏错误阶段，不重复创建账户或盲目重签，以免触发限额。证书签发成功不等于部署、续期或外网验证成功。

仓库只读工具检查单张本地叶证书的有效期与主机名：

    python3 scripts/certificate_check.py --cert /private/leaf.pem --hostname sub.example.com --min-days 7

它不读私钥、不联网、不修改配置，也不证明链信任或私钥匹配。部署前还要验证叶证书/私钥公钥一致、完整链受系统根信任、证书覆盖目标主机名。不得用curl -k掩盖失败。

## 4. 部署与回滚（需另行执行）

1. 备份现有Caddy配置与证书指向；新证书先进入独立staging目录。
2. 证书目录root:caddy 0750，证书私钥0640；DNS凭据保持root-only并隔离。使用acme.sh的install-cert复制机制，不让Caddy依赖acme.sh内部工作目录。
3. 完整检查链、主机名、有效期、密钥匹配，再原子切换版本目录的current符号链接。避免只替换一半证书文件。
4. 仅替换原有TLS获取方式为文件证书，保留其他受审阅路由与监听；先caddy validate再启动或reload。
5. 本机按真实主机名与系统信任库请求healthz，并比较实际提供的叶证书指纹。失败恢复旧文件/链接；不要盲目重启已知会失败的HTTP-01配置。
6. 从不经过同VPS退出节点的独立网络检查HTTPS主机名、端口、证书与正文。没有外部成功证据，不发布订阅。

## 5. 发布、续期和熟人分发

- 每人独立节点凭据与订阅令牌；节点认证、订阅下载、规则获取是三个不同验收项目。保留现有管理员UUID，先用临时客户端验证新成员与未注册凭据的行为。不要把暂时超时直接等同服务端明确拒绝认证。
- URL中的令牌等同访问凭据，禁止记录完整访问URL到公开日志。文件权限、目录列表、缓存与日志策略需要单独审阅；HTTPS只保护传输，不替代访问控制。
- 本地完整profile、provider片段和远程HTTPS订阅不能混为一谈。先验证真实下载和GUI刷新，再替换用户临时配置。保持Tailscale可恢复路径。
- 部署验收后才设置唯一每日续期计划，检查acme.sh内置cron和系统计划，避免重复。续期设计应覆盖 install-cert 部署 hook、reload、served 证书验收与失败通知；当前交付脚本只有 syslog 阶段日志，尚无已验收的外部通知。本次签发不是未来自动续期的证明。
- 待最终验收后清理明确归属的旧备份与临时规则。保留最近可用回滚，永久删除另需批准，不按通配符盲删。

## 已部署机制与验收分层

实际案例将节点数据面与订阅分发面分开：VLESS/REALITY负责代理认证与转发，Caddy HTTPS负责客户端下载配置；证书由独立acme.sh DNS-01流程取得并部署。两种服务不应共享DNS管理权限。订阅端口、节点端口与SSH管理端口各自独立核验，不能把HTTPS健康页通过当作VLESS协议通过。

目前两份独立订阅已发布，owner已选用远程配置。每次更新应检查客户端实际选择的远程配置，而不是编辑此前临时本地副本；生成器、托管内容与客户端刷新状态要使用同一版本来源，防止双轨。仓库保存流程与模板，不保存真实订阅URL、节点UUID或令牌。不可把所有成员的服务端users列表当客户端订阅发布。

9份MRS缓存实际下载是规则获取层证据。接下来只需在获准的规则模式下选择几个代表域名，查看实际连接的规则、策略组与出口；当前Direct模式和TUN关闭不证明按规则代理，也不证明浏览器UDP已接管。不要为了完成验收未经批准切换用户网络。

friend01本机正例仅说明保存的凭据在VPS本机测试中可用。其真实设备应独立导入、刷新并通过公网节点完成请求；测试不能经过同一VPS的Tailscale出口。订阅URL可获取、规则缓存存在、节点可认证、请求按规则路由、无旁路泄露，是五个分别记录的结论。


## 本轮复盘发现的续期缺口

- Let's Encrypt 已于 2025-06-04 停止到期邮件：[官方说明](https://letsencrypt.org/docs/expiration-emails/)。未设置通知时，不能假定 CA 会主动提醒。
- 外置证书文件在相同路径更新后，Caddy 是否真正重新读取，取决于实际 reload 流程。先只读检查 `systemctl show caddy -p ExecReload` 及 hook；核对 `caddy reload --force` 的适用性，见[官方命令说明](https://caddyserver.com/docs/command-line#caddy-reload)。标准官方 systemd unit 已有 `--force`，所以此处是核对点，不是已证实故障。不要仅为验证而重新签发或改动生产。
- 后续续期验收应同时比较磁盘证书与实际 served 叶证书指纹、正常证书链验证、有效期余量及独立公网访问。现有每日计划和首次成功只覆盖检查被执行；尚未覆盖未来真正续期、部署和失败通知。

## 订阅定制与刷新回路

通用生成器是基础模板，不是当前生产订阅的完整复现源。其离线输出没有 owner 的 SSH 精确 DIRECT 例外、没有同机订阅端点直连例外，也没有 DNS 块；TUN 默认关闭。分类 MRS 从可变的 `meta` 分支按每日间隔获取，之后内容可变。当前缓存的存在不保证将来的内容或匹配不变。

维护每人的定制清单，将基础模板、个人规则与发布版本分开。重生成前做脱敏配置差异比较，至少检查 SSH 例外、订阅刷新路径、规则顺序、组选择和 DNS/TUN 意图；可用合成输入建立回归样例，不将真实凭据写入测试。当前工具尚未实现定制合并或此类完整回归测试。

同机订阅有一种条件性风险：若客户端刷新 HTTPS 订阅时也通过此 VPS 节点，而代理 UID 禁止访问本机地址，请求可能被 guard 正确阻止。本轮未复现这个故障。后续验收要包含“代理已开启时刷新订阅”，先查刷新请求由谁发出、是否使用代理，再决定是否需要精确客户端例外；不扩大服务端本机访问权限，也不假定所有客户端刷新都会走系统代理。

## 可选的进一步缩权

目前域级 CAM 权限仍可影响该域多类 DNS 记录。未来如果需要进一步缩小泄露影响，可评估把 `_acme-challenge` 通过 CNAME/NS 委派到独立验证区，或在独立设备签发后部署，见[Let's Encrypt DNS-01 说明](https://letsencrypt.org/docs/challenge-types/#dns-01-challenge)。这是候选改进，不是本轮已实施的迁移。

随机订阅 URL 是 bearer 凭据。Caddy 默认隐藏一些认证头，不代表会自动隐藏 URL 路径或查询令牌；启用 access log、CDN、统计或错误收集之前，须审阅完整 URI 的记录、缓存与接收方，见[日志文档](https://caddyserver.com/docs/caddyfile/directives/log)。`no-store` 也不能撤回客户端已保存的节点凭据。外部 health 监测只需公开固定健康端点，不应拿带令牌的订阅地址做公共监测。
