# 日常维护与交接 Playbook

先读[部署备忘](deployment-record.md)，确认当前实例而不是照搬历史端口、UID、MTU。全部示例需在已有授权的服务器会话运行；默认先只读，不刷新软件源、切换代理、重启服务或删除数据。

## 一次检查四层

1. **管理/底座**：现有SSH密钥会话是否可用，UFW和Tailscale状态是否符合目标。不要关掉唯一可用管理通道来做测试。
2. **节点数据面**：Mihomo服务与当前PID的监听、目标端口防火墙、出站guard；独立外网客户端的真实HTTPS请求。
3. **订阅分发面**：Caddy证书、health、每人自己的HTTPS订阅下载与CRV实际选中配置；本地临时profile不是在线订阅源。
4. **观测面**：vps-usage报告新鲜度、最后成功时间、gap和累计数据。统计出错不自动证明节点故障。

## 只读首轮

```sh
systemctl is-active mihomo mihomo-guard tailscaled caddy mihomo-observed
systemctl is-enabled mihomo mihomo-guard tailscaled caddy mihomo-observed
vps-usage
```

一个服务inactive或报表陈旧时先确认它是否本来需要运行。日志可能包含端点或敏感配置，先本机检查、只分享脱敏错误阶段。不要贴完整配置、订阅URL、/connections响应或DNS凭据文件。

再按需要运行仓库 `vps_snapshot.sh`（输出地址需要脱敏）或 `wait_listener.py`（只证明当前PID拥有监听，不验证UID、认证或公网路径）。常驻统计工具模板的路径与账户有明确限制，不应未经复核换成其他位置。

## 软件更新窗口

先保存当前版本、配置与可用回滚，核对官方发行说明及当前包源。Ubuntu24内的安全更新与升级到下一发行版是两项不同操作；当前决定保留24。不要用切换发行版修复一个未定位的代理问题。

更新/重启后逐层复查：管理连接 → guard → 节点监听与真实请求 → HTTPS订阅 → 统计新鲜度。只见systemd active不够。新进程启动时UID和MainPID可能尚未稳定，使用有界等待并重新读取；若稳定身份仍错误，停止，不移除安全检查。

## 证书与续期

检查本地叶证书有效期可用 `certificate_check.py`。它不读私钥、不验证完整链，也不知道网络实际提供的是哪张证书。结合Caddy实际served叶指纹和正常CA校验核对；禁止以-k掩盖失败。

检查现有计划而不是再添加一份。当前案例03:23按服务器cron时区解释。首轮检查成功不代表到期时会续期。当前交付脚本只将阶段信息写入 syslog，没有已验收的外部失败通知；应保留回滚并定期核对到期余量，后续再按授权补齐告警。不要为了“证明续期”重复强制签发、消耗CA限额。Let's Encrypt 已于 2025-06-04 停止到期提醒邮件，不能依赖 CA 邮件补位。

外置证书路径不变时，需只读核对 Caddy 的实际 `ExecReload` 与是否使用 `--force`，确认续期 hook 能重新装载证书内容；这属于待验收风险，不是已经证实的生产故障。最终用正常 CA 校验和 served 叶证书指纹证明新证书生效。

## 订阅和熟人凭据生命周期

- 新增：生成独立凭据 → 受控注册 → 当前监听与正/负例认证 → 发布该人的配置 → 独立设备导入/刷新 → 实际请求。旧用户做回归。
- 修改规则：更新受控订阅源 → 客户端刷新 → 核对选中远程配置及MRS缓存 → 在获批规则模式验证几个实际连接。下载九个缓存只是获取层证据。
- 撤销：撤销订阅下载与撤销服务端节点UUID是两件事。缓存的旧配置仍可连接，除非服务端已拒绝它；既有连接是否中断也要核验。
- 保留一人一份策略和令牌，勿让熟人拿管理员身份。发给谁、发什么必须按本次批准，不把存在文件当作发送许可。

## 管理 SSH 与节点自回环

订阅把所有请求送往 VPS 时，客户端访问同一 VPS 的 SSH 可能先进入代理，再被禁止访问本机的出站 guard 正确拦截。先核对命中路径，不为解决管理连接放宽代理 UID 的自访问限制。

当前 owner 手机订阅已有精确例外：VPS IPv4 /32、TCP、SSH 23899 同时匹配才 DIRECT；用户反馈可用。这只影响该管理端点。若使用域名、IPv6、另一端口或另一份配置，须另行核对匹配，不扩大为整个 IP 直连。更新/重生成订阅前检查该定制项，通用生成器不会自动迁移它。

## 统计异常

- `connections:null`是官方空闲响应；不等于API故障。
- `gap/error`、`gap/delayed`或stale说明观测不完整，不按零流量处理。先看服务与权限，再看最近成功时间。
- 单个用户没有增长：可能是没有被采到的短连接，也可能标签/入站筛选不匹配；做持续下载并检查归属，不要将完整响应公开。
- Unix API有完整管理能力，官方该版本0666 socket不验secret；0700父目录是必要边界。不要chmod成可供其他人进入来“修复”采样。
- 数据库接近512MiB时此守护进程停止，避免无限占盘。不要清空水位解决空间问题；这会损失去重。先经授权备份，再制定保留与归档策略。

## 备份和失败续装

备份范围至少区分：运行节点配置、防护规则及单位文件、订阅源与成员记录、证书及更新流程、统计SQLite。秘密备份同样需私有权限并放在Git之外。SQLite用备份API或停止写入后复制；这不是普通多文件拷贝一致性保证。

失败时先保存脱敏阶段结果，核对原配置是否恢复、当前进程/端口和guard。查明残留归属后续装，不能盲删所有工作目录或再次套第一次安装器。删除旧备份必须先确认无需依赖其回滚，授权只覆盖指定材料。用户报告删除与独立核验要分别记录。

## 交接最小结果

交代：改了什么、为何、验证了哪条路径、仍未验证什么、下一步及回滚现在是否真的可用。只给当前一个必要动作，避免让用户重复切网或反复重跑已证实的测试。
